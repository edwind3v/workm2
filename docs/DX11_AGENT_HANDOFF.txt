1. EXACTLY WHAT WE KNOW ABOUT BAERIM
------------------------------------

1.1 Baerim uses Direct3D 11 at runtime [LOG]
A Baerim syserr excerpt from the user contains:
  DX11_DEVICE adapter=NVIDIA GeForce RTX 4060 Ti
      luid=00000000:00012570 vram_mb=3072
      render_index=0 render_outputs=2 display_adapter=0
      output=\\.\DISPLAY1 requested=1056x748 sync_interval=0
  DX11 renderer initialized: 1056x748, anti_aliasing=0

This is direct evidence of a DX11 renderer/device initialization code path.
It does NOT, by itself, enumerate all active draw passes, shaders, resources,
or prove that absolutely every onscreen object is drawn with D3D11. Do not
infer an exact swap-chain format, number of back buffers, or device lifetime
from these two log lines.

The "vram_mb=3072" value is what the application reported. It is not a
reliable measure of the RTX 4060 Ti's physical VRAM capacity.

1.2 Baerim's guild-mark texture atlas has recoverable addressing [LOG]
The reference log repeatedly reported:
  DX11_GUILD_MARK_DRAW file="mark/10_0.tga" index=113
    atlas=512x512 rect=272,36,288,48 srv=1 alpha=1.000
  index=62  -> rect=480,12,496,24
  index=173 -> rect=208,60,224,72
  index=11  -> rect=176,0,192,12

These examples exactly fit:
  atlas width 512; atlas height 512
  cell width 16; cell height 12
  columns = 512 / 16 = 32
  x0 = (index % 32) * 16
  y0 = floor(index / 32) * 12
  x1 = x0 + 16
  y1 = y0 + 12
For index 113: (17*16,3*12)-(18*16,4*12) = (272,36)-(288,48).
"sr v=1" in the log was written "srv=1"; likely denotes a valid/bound shader
resource view, but its internal type/value must still be checked [INFER].
Likewise "alpha=1.000" is a logged draw parameter, not proof of its blend mode.

There was also DX11_GUILD_MARK guild=0 mark=4294967295. The mark value equals
0xFFFFFFFF; it may be a sentinel, but its meaning is NOT established.

6. HOW TO FIND MORE INFORMATION IN BAERIM.EXE - REPEATABLE WORKFLOW
------------------------------------------------------------------
These steps are for reverse engineering binaries and assets the user owns
or is authorized to inspect. Operate on a copy, not the running production
installation. Avoid protection/anti-cheat bypass, credential extraction and
testing against third-party servers.

STEP A: Capture a reproducible evidence bundle
  Obtain, from the user with permission:
    baerim.exe (the EXACT binary matching the logs)
    complete shadercache folder, preserving original directory names
    relevant non-secret config files, syserr/log.txt
    the character/costume's GR2 plus referenced DDS/TGA assets if available
    screenshot of Baerim character and clean preview at same pose/view
    the clean branch commit SHA / game build timestamp
  Include SHA-256 of every input and record whether 32-bit or 64-bit.
  Keep a MANIFEST with exact filename, hash, size, extraction date, origin.
  Do not assume old previous-chat attachments remain accessible.

PowerShell examples (read-only, run locally):
  Get-FileHash -Algorithm SHA256 .\baerim.exe
  Get-ChildItem .\shadercache -Recurse -File |
      Get-FileHash -Algorithm SHA256 |
      Export-Csv .\shader_hashes.csv -NoTypeInformation
  Get-ChildItem .\shadercache -Recurse -File |
      Select-Object FullName,Length

STEP B: Inspect PE architecture/imports
  In a VS Developer Command Prompt:
    dumpbin /headers baerim.exe
    dumpbin /imports baerim.exe
  Check PE machine type, imported D3D9/D3D11/DXGI/D3DCompiler APIs,
  CLR/native status, resources, version and manifest.
  A missing d3d11.dll import does NOT disprove DX11; code may load a DLL
  dynamically. Conversely, one imported function does not prove usage.
  For runtime corroboration use Microsoft Process Explorer (lower pane
  DLLs) or ListDLLs, and note when modules appear.

STEP C: Search Baerim's strings and trace callers
  Import the EXE in Ghidra (or another authorized PE analyzer).
  Run analysis and find ASCII/UTF16 strings, including:
    DX11_DEVICE
    DX11 renderer initialized
    DX11_GUILD_MARK
    DX11_GUILD_MARK_DRAW
    model_preview / model_shadows / terrain / water / smaa
    shadercache, HLSL, .cso, .dxbc, .dds, .tga
    anti_aliasing, sync_interval, shadow, graphics settings
  For each string, inspect ALL references to its address, not just the
  displayed function. Rename functions by a PROVEN role, e.g.
    LogDx11DeviceInfo_Candidate
    DrawGuildMarkAtlas_Candidate
  Keep an index: original address/RVA, hash of matching EXE, caller/callee
  graph, referenced globals, API calls, observed log text and confidence.
  Different Baerim builds shift addresses; NEVER publish unsourced offsets.

Inspect calls/patterns corresponding to:
    D3D11CreateDevice or D3D11CreateDeviceAndSwapChain
    DXGI factory/swap chain creation; Present/ResizeBuffers
    ID3D11Device::CreateBuffer/CreateTexture2D/Create*Shader
    ID3D11DeviceContext::*Set*, Draw*, Dispatch, Map/Unmap
    shadow/depth targets, resource sharing, shader creation from bytes
  Virtual COM calls may not show as named imports; identify interface
  vtable slots only after proving the interface pointer type.

STEP D: Analyze every original shadercache object
  First inspect byte signatures and sizes; do not rely on extensions.
  DXBC indicates a DirectX shader container; inspect its actual chunks.
  Where applicable, use Windows SDK tools such as:
    fxc /dumpbin <shaderfile>
  Or use a small trusted disassembler based on Microsoft
    D3DDisassemble(...)
  And reflection based on:
    D3DReflect(..., IID_ID3D11ShaderReflection, ...)
  Record for EACH shader in a machine-readable inventory:
    original filename, SHA256, shader stage/profile
    input/output semantics
    all constant buffers: register, byte size, variable name/offset/type
    all textures/SRVs/UAVs, sampler slots and resource dimensions
    thread-group sizes for compute shaders
    feature/variant flags inferred from bytecode
    names or strings tying this shader to pass initialization [if any]
  Disassembly/reflection gives an implementation contract; it does not
  reveal original C++ class names or live pass order.
  Particularly compare model_preview_vs/ps against our HLSL and verify
  whether t7/s1/b1 layout from previous notes matches real original bytes.
  NEVER declare the 123 programs all active based only on shader creation
  in a standalone test host.

STEP E: Inspect runtime I/O without injecting into the game
  Process Monitor: filter Process Name = baerim.exe; inspect File Create/Open
  and Read events for shadercache, config, shaders, effects, DDS/GR2 files,
  pack archives and logs. Capture game startup, map load, costume change.
  Process Explorer/ListDLLs: inspect loaded D3D libraries and paths.
  Pair events with exact timestamps in syserr.txt.
  Distinguish asset load time from GPU upload/draw time; ProcMon does not
  show D3D11 draw calls. Do not interpret a cached file read as proof of
  a corresponding shader draw.

STEP F: GPU frame capture only in permitted/instrumentable conditions
  RenderDoc works on the standalone DX11 host but failed to inject into
  both the reference client and a clean Metin2 client. Do not waste time
  repeating identical failed injection attempts with no new hypothesis.
  Check architecture, app startup path, API compatibility, logs and tool
  version. Use RenderDoc on a legitimate development build that permits
  capture; do not evade protective software to force an injection.
  PIX may offer D3D11-through-D3D11On12 capture under specific Windows/API
  conditions, with limitations. Verify compatibility with this 32-bit
  game and current tool version before promising it will work.
  If no frame capture is available, prioritize static PE analysis, shader
  reflection, non-invasive OS monitoring, and comparisons with our own
  instrumented clean-client build.

If a frame is captured successfully, build a PASS LIST rather than
scrolling arbitrarily:
    Pass name/order; render/depth targets/formats/dimensions
